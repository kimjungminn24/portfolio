## 문제

단독 스팟을 등록할 때 **반경 50m 이내에 같은 종류의 데이터가 있는지** 확인하는 기능이 있어요. 등록이 몰리는 상황을 가정해 부하 테스트를 돌렸더니 실패율이 20% 에 달했어요.

## 가설

인덱스 방식에 따라 성능이 어떻게 달라지는지 다섯 가지 가설을 세워 비교했어요.

1. 인덱스 없이 `ST_Distance_Sphere` 로 거리 계산
2. 인덱스 없이 사각형 범위 필터 후 Java 거리 계산
3. 복합 인덱스 `(lat, lng)` + 사각형 범위 필터 후 Java 거리 계산
4. 공간 인덱스 + `MBRContains` + `ST_Distance_Sphere`
5. 공간 인덱스 + `MBRContains` + Java 거리 계산

## 측정 결과

| | 가설 1 | 가설 2 | 가설 3 | 가설 4 | 가설 5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Latency P95 (ms) | 9,768 | 2,543 | 15 | 12 | 7 |
| RPS | 49.68 | 82.99 | 95.15 | 95.06 | 95.06 |
| 실패율 | 8.9% | 0 | 0 | 0 | 0 |

## 판단

- **거리 계산 방식(Java vs DB)**: 사각형 필터를 거친 후보군 데이터가 적어서 성능 차이가 거의 없었어요.
- **공간 인덱스**는 성능이 가장 좋았지만, 기존 서비스에 적용하려면 `Point` 컬럼 추가와 SRID 설정이 추가로 필요했어요.
- **복합 인덱스**는 사각형 범위 필터와 자연스럽게 결합되고 JPA 로 구현이 쉬웠어요.

성능과 개발 효율을 함께 고려해 ==복합 인덱스 (가설 3)== 를 선택했어요.

## 성과

Artillery 부하 테스트 결과 **실패율 0%** 에 도달했고, P95 지연이 9,768ms 에서 12ms 로 줄었어요.
