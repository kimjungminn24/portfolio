## 문제가 생긴 이유

짧은 시간에 같은 URL로 요청이 반복해서 몰리면서 CPU 사용률이 약 90%까지 올랐고, 서버가 멈췄습니다.

Nginx 접근 로그를 확인해 보니 일반 요청 사이에 `.env` 같은 민감한 파일을 찾는 요청과 `sqlmap` 같은 점검 도구의 User-Agent가 섞여 있었습니다. 프로세스가 멈춘 정확한 원인까지는 단정하지 않았지만, 서비스를 다시 실행하는 것만으로는 같은 일이 반복될 수 있다고 판단해 차단 규칙과 로그 확인 환경을 함께 구성했습니다.

## 요청 차단

- **Bad Bot Blocker**: Nginx용 차단 규칙 모음(nginx-ultimate-bad-bot-blocker)을 적용해, `sqlmap` 같은 알려진 악성 User-Agent는 응답 없이 연결을 끊습니다(444).
- **요청 수 제한**: 비로그인으로도 등록과 피드백을 할 수 있어서 쓰기 요청을 따로 제한했습니다. 요청이 넘치면 429를 돌려줍니다.

| 구분 | 제한 (IP 기준) |
| --- | --- |
| API 전체 | 초당 10건 |
| 스팟 등록 | 분당 10건 |
| 피드백 | 분당 10건 |
| 의견 제출 | 분당 5건 |

- **Fail2ban**: `.env`, `.git` 같은 경로를 찾거나 Bad Bot Blocker(444)에 걸린 요청이 60초 안에 5번 쌓이면, 그 IP를 1시간 동안 차단합니다.
- **노출 줄이기**: `server_tokens off`로 Nginx 버전을 숨기고, 숨김 파일은 외부에서 접근하면 403을 돌려줍니다. 도메인이 아니라 IP로 직접 들어오는 요청은 연결을 끊습니다.

## 로그 모니터링 구축

서버에는 Promtail만 두고, 로그는 Grafana Cloud(Loki)로 보내도록 구성했습니다. Promtail은 systemd 서비스(`Restart=always`)로 등록해 항상 수집하도록 했고, 서버 상태와 보안 이벤트는 Slack 알림으로 받습니다. Grafana에서는 검색 API 로그를 데코 유형별로 집계해, 어떤 유형의 검색이 많이 일어나는지도 확인할 수 있습니다.

```
sum by(type) (
  count_over_time(
    {job="nginx"} |= "/api/decors/search"
    | regexp "type=(?P<type>[^& ]+)" [24h]
  )
)
```

## 결과

적용한 뒤 직접 요청을 보내 확인한 결과입니다.

| 확인한 요청 | 응답 |
| --- | --- |
| `sqlmap` User-Agent 요청 | 444 (연결 끊김) |
| `/.env` 접근 | 403 |
| IP로 직접 접근 | 444 (연결 끊김) |
| 반복 악성 요청 IP | 60초에 5번이면 1시간 차단 |

이전에는 서버에 문제가 생긴 뒤에야 원인을 찾을 수 있었지만, 이제는 로그와 알림으로 서버 상태와 비정상적인 요청을 확인할 수 있습니다. 이후 같은 유형의 서버 다운은 다시 일어나지 않았습니다.

서버를 다시 실행하는 것으로 끝내지 않고, 원인이 된 요청을 로그에서 찾아 차단과 관측을 함께 갖춰야 같은 문제가 반복되지 않는다는 것을 배웠습니다.
